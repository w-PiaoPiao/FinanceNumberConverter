## 3. 命名规范

| 类型 | 规范 | 示例 |
| --- | --- | --- |
| 文件 | PascalCase | `NumberConverter.ets` |
| 类 / 接口 | PascalCase | `NumberConverter` |
| 函数 / 变量 | camelCase | `convertToChinese` |
| 常量 | UPPER_SNAKE_CASE | `MAX_ITEMS` |
| 装饰器 | @PascalCase | `@State` `@Component` |
| 资源文件 | snake_case | `string.json` |

## 4. 代码风格

- **强制**：每个公开函数有 JSDoc 文档注释
- **强制**：函数体不超过 30 行
- **强制**：优先 `const` 而非 `let`
- **强制**：金额用 `number`（双精度）+ 手动截断（与 iOS Decimal / Kotlin BigDecimal 不同的设计）
- **强制**：UI 文案硬编码中文（不做 i18n）
- **强制**：状态用 `@State` 装饰器私有属性
- **推荐**：使用 `interface` 替代 `class`（ArkTS 推荐风格）

## 5. 关键技术决策

### 5.1 为什么用 number 而不是 decimal？
HarmonyOS NEXT **没有** `Decimal` 类型。ArkTS 用 `number`（IEEE 754 双精度）。
- **缓解**：金额最大 12 位整数 + 2 位小数 = 14 位有效数字，远低于 15-17 位双精度精度
- **代码**：所有计算用 `Math.round(x * 100) / 100` 截断到分
- **风险**：理论上有精度损失，实测财务场景可控

### 5.2 为什么 Stage 模型？
Stage 是 HarmonyOS NEXT 主推的应用模型，旧的 FA 模型已不推荐。
- 清晰的 Ability / Page / Component 三层
- 更好的生命周期管理
- 与 ArkUI 完美配合

### 5.3 为什么零三方依赖？
- 学习友好：少一层黑盒
- 包体小：.hap < 1MB
- 可靠性：HarmonyOS 生态年轻，依赖可能有兼容性问题
- **所有功能用 HarmonyOS API 内置能力实现**

## 9. 与 iOS / Android 的差异

| 项 | iOS (Swift) | Android (Kotlin) | Harmony (ArkTS) |
| --- | --- | --- | --- |
| 类型 | `Decimal` | `BigDecimal` | `number` |
| UI | SwiftUI | Jetpack Compose | ArkUI |
| 状态 | `@State` | `remember { ... }` | `@State` |
| 复制 | `UIPasteboard` | `ClipboardManager` | `pasteboard` |
| 测试 | XCTest | JUnit 4 | Hypium |
| 数字格式 | `NumberFormatter` | `DecimalFormat` | `Number.toFixed` + 手动处理 |
| 模型 | — | MV 极简 | Stage 模型 |
| 入口 | `@main App` | `ComponentActivity` | `UIAbility` |
| 异步 | `Task` | `coroutine` | `Promise` / `async` |

**核心算法 1:1 翻译**：分组逻辑、零处理、单位拼接完全一致。
