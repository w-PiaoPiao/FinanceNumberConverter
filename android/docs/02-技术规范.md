## 3. 命名规范

| 类型 | 规范 | 示例 |
| --- | --- | --- |
| 文件 | PascalCase | `NumberConverter.kt` |
| 类 / 对象 | PascalCase | `NumberConverter` |
| 函数 / 变量 | camelCase | `convertToChinese()` |
| 常量 | UPPER_SNAKE_CASE | `MAX_ITEMS` |
| Composable | PascalCase | `ConverterScreen` |
| 包名 | 全小写 | `com.example.financenumberconverter` |

## 4. 代码风格

- **强制**：每个公开函数都有 KDoc 文档注释
- **强制**：函数体不超过 30 行
- **强制**：优先 `val` 而非 `var`
- **强制**：金额一律用 `BigDecimal`（避免 Double 精度问题）
- **强制**：UI 文案硬编码中文（不抽到 strings.xml，便于维护）
- **强制**：状态用 `remember { mutableStateOf(...) }` 私有
- **推荐**：使用 `data class` 而非手动写 equals/hashCode

## 5. 关键技术决策

### 5.1 为什么用 BigDecimal 而不是 Double？
与 iOS 一致：财务场景严禁浮点误差。`BigDecimal` 是定点数，零误差。

### 5.2 为什么用 Compose 而不是 XML？
- 声明式，类 SwiftUI 体验
- 代码量更少
- 现代化趋势（Google 全力推 Compose）
- 学习资源丰富

### 5.3 为什么零三方依赖？
- 学习友好：少一层黑盒
- 可靠性：不担心依赖过期、作者弃坑
- 包体小：APK < 3MB
- **所有功能用 AndroidX + Material 3 内置 API 实现**

### 5.4 为什么 minSdk = 29？
- 覆盖 85%+ 设备
- 跳过老设备的兼容代码
- 用更现代的 API（如 `getSystemClipboardManager` 改进）
- 与用户实际手机（安卓 15/16）完全兼容

## 6. 构建变体

## 9. 与 iOS 项目的差异

| 项 | iOS (Swift) | Android (Kotlin) |
| --- | --- | --- |
| 类型 | `Decimal` | `BigDecimal` |
| 输入 | `Decimal` | `BigDecimal` |
| UI | SwiftUI | Jetpack Compose |
| 状态 | `@State` | `remember { mutableStateOf }` |
| 复制 | `UIPasteboard` | `ClipboardManager` |
| 错误提示 | `@State errorMessage` | `var errorMessage by remember` |
| 测试 | XCTest | JUnit 4 |
| 数字格式 | `NumberFormatter` | `DecimalFormat` |

**核心算法 1:1 翻译**：分组逻辑、零处理、单位拼接等完全一致。
